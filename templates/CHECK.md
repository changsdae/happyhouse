# {{ROUND}} 독립 검증

## 검증 기준

- 검증담당: 미작성
- 기록 시각: 미작성
- 원문과 계획 근거: 미확인
- 계획 기준: 초안
- 코드 기준 파일: 미지정
- 마지막 실행 시각: 미작성
- 기대결과 작성: 미실시
- 현재 판정: 미실행
- 기록 점검: 미실시

검증담당이 실제로 원문에서 기대결과를 먼저 작성했으면 `기대결과 작성: 구현 열람 전 작성`으로 표시합니다.
이미 구현을 본 세션이라면 독립 작성했다고 바꾸지 말고 새 검증 세션에 기대결과 작성을 맡깁니다.
코드 기준 파일은 테스트 **전에** capture로 만든 `[기준](runs/basis-0001.json)` 형태의 링크입니다.
마지막 실행 시각은 실제 시각을 시간대와 함께 기록합니다. 예: `2026-10-31T10:30:00+09:00`.
기능은 `현재 판정: 통과`, 기록 점검은 `기록 점검: 충족`일 때 완료 후보가 됩니다. 실행 전·실패·보완 중에는 그대로 표시합니다.

## 사용 시나리오

사람이 서비스를 사용하는 장면을 2~4문장으로 적습니다. 시작 조건 → 행동 → 기대결과 → 아래 사례 번호 순으로 연결합니다.
예시는 실제 과제의 원문을 대신하지 않습니다. 시나리오 전문을 테스트마다 복사하지 않습니다.

## 검사 설정

AI가 제품·테스트·문제 원문·설정·고정 입력 데이터 중 이번 검증에 필요한 경로를 지정합니다. 모든 경로는 Workspace 기준입니다.
언어나 프레임워크는 제한하지 않습니다. `inputs`는 실제 파일/디렉토리, `exclude`는 제외할 생성물 경로입니다. 글로 제외 이유를 남깁니다.
전체 Workspace(`.`)나 계속 갱신되는 PLAN/WORK/CHECK/RESUME/runs 자체를 inputs에 넣지 않습니다.
완료조건 변경은 WORK의 라운드 계약으로 별도 감지합니다. 이 외 요구·계획 변경은 개정과 영향 검토를 기록합니다.

```happyhouse
{"inputs": [], "exclude": []}
```

입력 범위의 충분성과 환경·외부 서비스 변경은 검증담당이 확인합니다. 범위를 바꿔 과거 통과를 재사용하지 않습니다.

## 문제 유형과 기대결과

해당 라운드에 의미 있는 정상·경계·실패 유형을 나눕니다. 원문상 정답이 불분명하면 ‘판정 보류’로 기록하고 질문합니다.

| 번호 | 유형 / 확인할 문제 | 입력·조건 | 기대결과 | 정답 근거 | 실제 결과 | 판정 | 실행 증거 |
|---|---|---|---|---|---|---|---|

번호는 이 문서 안에서 01, 02처럼 간단히 씁니다. 실제 출력에 맞춰 기대결과를 바꾸지 않습니다.
표는 현재 기준으로 필수 검증할 사례만 담고, 완료 후보일 때 각 행의 판정은 `통과`, 실행 증거는 로컬 파일 링크여야 합니다.
이전 실패 실행은 runs에 보존하고 수정 이유를 WORK로 연결합니다. 실패 사례를 이유 없이 삭제해서 완료시키지 않습니다.

## 서로 다른 근거

- 원문 요구사항과 테스트가 빠짐없이 연결되는지 확인
- 독립 손계산 / 원문 예제 / 별도 규칙 중 적용 가능한 정답 근거
- 일부러 틀린 출력·실패 입력을 별도 fixture에서 주어 검증기가 실패를 잡는지 확인
- 이번 라운드 + 이전 라운드 연결 + 영향받은 기능의 회귀검증
- 최종 사용 흐름을 처음부터 끝까지 실행 (최종 라운드 필수)

동일 프롬프트를 두 번 실행하거나 두 AI가 동의하는 것만으로 독립 검증했다고 쓰지 않습니다. 모든 항목을 기계적으로 강제하지 않고 적용 여부와 이유를 기록합니다.

## 실행 기록

| 실행 번호 | 실행자 / 시각 | 코드 기준 / 계획 개정 | 명령·환경 | 기대 vs 실제 | 종료코드 / 로그 | 결론 |
|---|---|---|---|---|---|---|

로그는 runs/에 새 파일로 보존합니다. 미실행·실행 불가·실패·통과를 구분합니다. 주담당이 대신 실행했다면 ‘주담당 실행, 검증담당 증거 검토’라고 적습니다.
통과 후 코드/기대조건이 바뀌면 해당 범위의 통과를 그대로 재사용하지 않습니다.

## 변경 영향과 필수 기록 점검

기대결과를 먼저 보존하고 실행한 뒤, 변경된 코드와 호출·데이터 연결을 살펴 빠진 검증을 찾습니다.
추가 검증의 기대결과도 원문·확정 요구에서 도출하며 구현 결과에 맞춰 고치지 않습니다.

- 변경된 코드 / 영향 라운드 / 영향 없다고 판단한 범위와 이유:
- 원문 → 사례 대응 / 이전 기능 연결·재검증 근거:
- WORK의 선택 근거·기대효과·위험·실행 허용 범위 확인:
- SUMMARY·인계의 내용 및 근거 링크 확인:
- 남은 누락 / 추가 결정 / 다음 행동:

기능 통과와 기록 점검 충족을 각각 판단합니다. 검사 프로그램의 성공을 제품 테스트나 승인 진위 확인으로 대체하지 않습니다.
