# Happyhouse

**Markdown으로 계획·대화·검증·이해를 기록하고, 작은 검사 도구로 기록 누락과 검증 기준 변경을 확인하는 협업 키트**입니다. AI가 지침을 읽고 Workspace에 폴더와 문서를 직접 만들고 갱신합니다. 화면 서버나 대시보드는 없습니다.

## 1. 가져오기

문제와 코드가 있는 Workspace에서 실행합니다.

```sh
git clone https://github.com/changsdae/happyhouse.git _harness/happyhouse
```

이미 같은 위치에 받았다면 다시 clone하지 않습니다. 기존 원본 변경 여부를 확인한 뒤 필요한 경우 `git -C _harness/happyhouse pull --ff-only`로 갱신합니다. 이 키트를 사용하는 동안 내려받은 원본은 수정하지 않습니다.

## 2. 두 세션에서 시작

두 터미널 모두 같은 Workspace를 엽니다. 각 AI 세션에 [START.md](START.md)의 해당 요청문을 복사해 전달합니다. 요청문은 터미널 셸 명령이 아니라 **AI에게 보내는 채팅**입니다.

1. 주담당에 ‘첫 요청: 준비’를 전달합니다. AI가 [SETUP.md](SETUP.md)에 따라 폴더와 빈 문서를 만들고 기록 준비 검사를 실행합니다. 직접 mkdir로 하나씩 만들 필요가 없습니다.
2. 주담당에 ‘문제 이해와 계획’을 전달하고 목표·완료조건을 대화로 구체화합니다.
3. 계획 초안이 나오면 다른 세션에 ‘검증담당 첫 요청’을 전달합니다.
4. 검토 내용을 주담당에게 읽히고 반영할 사항을 정한 뒤 구현 범위를 승인합니다.

- 주담당: 원문 이해 → 계획 → 사용자 결정 → 구현·자체 테스트 → 기록·로컬 Git 커밋
- 검증담당: 원문·계획 독립 검토 → 구현 내부를 보기 전 기대결과 작성 → 코드 기준 저장·실행 → 코드 변경 영향·필수 기록 확인

상대 세션이 자동으로 움직이지는 않습니다. “validation/PLAN_REVIEW.md를 읽고 반영할 내용을 설명해줘”처럼 파일을 지정해 전달하면 됩니다.

## 3. 내가 계속 볼 문서

에디터를 나누어 왼쪽에는 **docs/PLAN.md**, 오른쪽에는 **현재 works/Rn/WORK.md**를 Markdown 미리보기로 엽니다. AI가 파일을 저장하면 미리보기에서 확인합니다. 자동으로 반영되지 않는 에디터에서는 다시 열거나 새로고침합니다.

PLAN은 짧은 전체 표와 체크리스트, WORK는 지금 답할 질문과 대화·결정·인계입니다. 실행이 끝나면 **docs/REVIEW.md**로 전체 서비스를 복습합니다. 파일을 만드는 것만으로 구현이나 검증이 끝났다고 표시하지 않습니다.

## 실제 작업 구조

```text
Workspace/
├── AGENTS.md, README.md, 제품 코드       제공된 내용 보존
├── _harness/happyhouse/                  지침 원본
├── docs/
│   ├── PLAN.md                         전체 목표·라운드 표
│   ├── REVIEW.md                       전체 시스템 이해·복습
│   └── RESUME.md                       최신 인계·짧은 전환 이력·재개 요청
├── works/R1/WORK.md                     현재 대화·결정·이해 확인·인계
├── validation/
│   ├── PLAN_REVIEW.md                   계획 검토
│   └── R1/
│       ├── CHECK.md                    기대결과·실행 판정
│       └── runs/                       실제 검증 로그·basis-0001.json 등
├── results/R1/SUMMARY.md                누적 결과·실행법·한계
└── dump.md                             자유 메모
```

문제를 이해하기 전에는 라운드 폴더를 만들지 않습니다. R1·R2를 정하면 AI가 각 폴더를 만듭니다. 제품 코드는 기존 구조에서 누적 구현하고 results에는 요약과 실제 산출물만 둡니다.

## 기록 검사

Python 3.9 이상만 있으면 추가 패키지·Git 연동·네트워크 없이 실행합니다. 제품 언어는 Python일 필요가 없습니다. 검사할 파일/폴더는 CHECK에 프로젝트별로 지정합니다. [CHECKER.md](CHECKER.md)에 범위와 한계를 설명했습니다.

```sh
python3 _harness/happyhouse/check.py ready
python3 _harness/happyhouse/check.py capture R1
python3 _harness/happyhouse/check.py check R1
python3 _harness/happyhouse/check.py check --all
```

위 명령은 한꺼번에 실행하는 초기화 절차가 아닙니다. 순서대로 **준비 후 / 실제 테스트 전 / 라운드 완료 전·후 / 최종 점검**에 AI가 실행합니다. 준비 검사는 제품 실행 환경이나 정답을 보증하지 않습니다. 종료코드 1이면 누락·불일치를 보완합니다. 검증담당은 기능과 근거의 타당성을 별도로 확인합니다.

## 개발 선호와 이해

웹 서비스를 만들어야 하고 문제의 제약에 맞으면 **Python + Streamlit을 기본으로 사용**합니다. 기존 코드·필수 기술·API 요구와 맞지 않으면 이유를 설명하고 대안을 정합니다. 상세 선호는 [PREFERENCES.md](PREFERENCES.md)에 있습니다.

라운드가 끝날 때 핵심 동작과 선택 이유를 짧게 확인하고, 마지막에는 입력 하나를 끝까지 따라 실행하며 복습합니다. AI가 작성한 설명과 사용자가 직접 설명해 확인한 내용을 구별합니다. [USER_GUIDE.md](USER_GUIDE.md)에 사람이 확인할 순서를 적었습니다.

## 범위

상태·승인은 문서로 기록합니다. 실행 범위 안의 오류 수정에는 반복 승인 대신 필요한 재검증을 수행합니다. 필수 기록·기준 일치는 도구로 확인하고 근거의 타당성은 검증담당이 확인합니다. 검사 프로그램이 사람의 승인 진위나 제품 정답을 판정하거나 파일 편집을 차단하는 것은 아닙니다. 시험의 도구·통신·제출 규칙을 우선 따르며 시험 문제·데이터·작업 로그를 이 공개 키트에 올리지 않습니다.

키트 버전: 2.1 (2026-10-31). Markdown 운영에 준비·완료 검사, 변경 영향 검토, 최신 인계를 보완했습니다. 제품 버전·계획 개정과는 별개입니다. 라이선스는 아직 지정하지 않았습니다.
