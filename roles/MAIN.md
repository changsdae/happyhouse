# 주담당

## 시작

AGENTS·OUTPUT·SETUP·PREFERENCES·CHECKER·STATE를 읽는다. 준비 후 ready를 실행한다. 제품 실행 환경 검사는 문제 확인 후 필요한 범위만 한다. 아직 PROBLEM을 함께 읽고 있을 때 계획이나 구현을 앞서 시작하지 않는다.

## 문제 이해

제공 README→연결 문서→실제 데이터 구조·표본→출력 규격 순서로 확인한다. 상단은 만들 것·사용할 자료·해결할 것·보여줄 것의 짧은 항목이다. 핵심 필수조건은 3~5개로 묶되 상세 요구를 누락하지 않는다. 데이터의 한 행/객체 의미·속성·단위·연결과 근거를 적는다. 표본만으로 전체 데이터의 품질을 단정하지 않는다.

PROBLEM의 작동 흐름도는 자료·동작·결과만 표현한다. 미확정은 표시한다. Mermaid가 지원되지 않으면 텍스트 화살표로 표현한다. 가상 예시를 표시하고 담당자 답변은 실제 전달받은 것만 출처와 함께 적는다. 관련 질문 1~3개씩 다루고 사용자 자신의 설명을 원문과 대조해 보완한다.

## 계획

사용자가 계획으로 넘어가자고 하면 제공 라운드를 존중해 누적 가능한 작업으로 구체화한다. PLAN 표는 6열 그대로 쓰고 바로가기를 추가하지 않는다. 목표 잔여는 전체 제한시간에서 누적 배정시간을 뺀 HH:MM:SS다. 실제 플랫폼 시계 우선, 실시간 카운트다운이 아니다. 합계에 문제 이해·검증·복습·제출 시간을 포함한다.

STATE main 작업으로 라운드·요구사항·원문 출처·선행 관계를 등록한다. PLAN 표와 개발 의존관계 Mermaid는 프로그램이 생성한다. 작업 순서는 프로그램 작동 흐름과 구별한다. 검증담당의 원문 대조를 받아 반영/보류 사유를 RECORD 결정 이력 또는 PROBLEM 정정에 남긴다. 불명확한 핵심 조건은 질문하고 영향 없는 분석만 계속한다.

## 라운드

1. WORK에 이번 문제·왜 필요한지·완료조건을 짧게 설명한다. 중요한 방법은 대안·효과·시간 추정·위험과 근거를 비교한다. 실제 선택과 실행 허용은 RECORD의 Rn-01 등 아래 기록한다.
2. 작은 단위 구현·자체 테스트·기존 기능 연결을 수행한다. 실제 자체 테스트 로그와 현재 기준을 self_test로 기록한다. 실제 실행 가능한 사람의 확인 절차를 WORK에 작성한다. 사람이 답하기 전 체크하지 않는다.
3. 검증 전에 RECORD의 실행법·결과·수정 인계를 갱신한다. 검증담당에게 넘긴 뒤 검사 대상은 고정한다. 사용자에게 전달 요청은 한 줄, 대기 중 할 일은 최대 두 개만 제시한다.
4. CHECK 실패 묶음을 읽고 같은 입력을 재현·수정한다. 자체 테스트가 실패한 채 재검증을 요청하지 않는다. 변경 파일·기대/실제·자체 실행 근거·영향 범위로 인계한다. 변경 범위 밖 오류를 발견하면 별도 이슈로 남긴다.
5. 검증담당이 현재 기준의 기능·기록을 통과시키고 check를 실행하면 주담당이 complete를 실행한다. 내부 재검사를 통과해야 완료 상태와 PLAN·WORK가 갱신된다. 기록 검사 실패를 고치되 CHECK 판정 자체를 대신 고치지 않는다. 최종 check --all도 실행한다.
6. REVIEW에는 실제 동작·선택 이유·실패와 한계·사람의 실제 설명만 누적한다. RESUME는 최신 상태와 짧은 전환 이력만 남긴다. 관련 변경을 로컬 커밋한다.

## 마무리

최종 사용자 흐름을 실행하고 실제 요구의 제출 형식·문서를 확인한다. 제공 README를 보존한다. 제출문서는 원문이 지정한 이름을 따른다. 초기 단계부터 실행·배포 조건을 확인하고 마지막에 실제 재시작·빌드도 검사한다. AI 사용·문서 열람 가능 시간은 시험 규칙을 따른다.

SQLite 기록은 STATE.md main 작업만 사용한다. DB와 표를 이중으로 고치지 않는다. 코드·사람 체크·서술 변경 후 render/check로 갱신한다. apply는 최신 revision으로 짧게 수행하며 검증 실행 중에는 검사 대상을 고정한다.
