# 주담당

## 시작과 계획

1. Workspace 지침 → 키트 AGENTS·SETUP·PREFERENCES·CHECKER → RESUME의 현재 인계, PLAN과 현재 WORK를 읽는다. 첫 준비 요청이면 SETUP에 따라 없는 파일만 만들고 `check.py ready`로 기록 준비를 확인한다. 제품 실행 환경은 별도 점검한다.
2. 제공 README와 연결된 문제 원문을 읽고 출처를 적는다. 목표·사용자·입출력·필수 기능·완료조건·제약을 함께 구체화한다. 불분명한 부분만 질문한다.
3. 제공 라운드를 존중하고, 없으면 누적 실행 가능한 R1·R2로 나눈다. 각 WORK에 입력·처리·출력·연결·완료조건을 적는다. 웹 구현에는 PREFERENCES의 Python+Streamlit 기본값을 적용하되 과제 조건과 충돌하면 먼저 설명한다.
4. 목표를 정한 뒤 난이도·시간을 배정한다. PLAN 표는 한눈에 보이게 짧게 유지하고 상세 내용은 WORK로 연결한다. 계획20 + 라운드130 + 마무리30은 180분 예시다. 실제 제한과 제출 시간에 맞춘다. 시간 합계를 직접 계산하고 검증담당에게도 확인받는다.
5. 검증담당에게 원문·계획을 인계하고 제안을 사람에게 설명한다. 반영/보류 이유를 기록하고 중요한 변경은 다시 검토한다. 현재 범위 실행 승인 후 구현을 시작한다.

## 한 라운드의 반복

- 시작할 때 PLAN의 현재 라운드와 WORK 상단의 질문·승인 범위·다음 행동을 갱신한다.
- 큰 결정만 후보·기대효과·근거/가정·구현 시간·위험·확인 방법·추천·포기한 점을 비교한다. 사실·예상·미확인을 구분한다. 선택 전 검증담당이 요구 적합성과 위험을 검토하고, 구현 후 선택한 방법의 실제 효과를 검증한다. 선택하지 않은 후보를 모두 구현하지 않는다. 선택 이유와 실행 허용 근거를 R1-01 같은 대화 번호에 기록한다. 같은 논점의 답변·수정은 같은 번호에 누적한다.
- 작은 단위로 기존 제품 코드에 구현 → 자체 테스트 → 이전 라운드와 연결한다. 라운드마다 코드 복제본을 만들지 않는다.
- 관련 변경만 로컬 Git 커밋한다. 저장소가 없다면 상위 저장소와 제출 규칙을 확인해 작업 저장소를 준비한다. 작성자 이름/메일이 없으면 확인하고 만들지 않는다. 내려받은 키트와 무관한 변경은 stage하지 않는다.
- WORK에 계획 기준·공개 실행법·입출력 계약·검사 대상 경로를 적어 검증담당에게 넘긴다. 검증담당이 테스트 전 capture로 실제 파일 기준을 저장한다. 미커밋 코드까지 기준에 포함하고 검증 중 대상 코드·고정 입력은 바꾸지 않는다.
- 검증담당의 CHECK를 읽고 실패를 재현·수정한다. 바뀐 코드/요구와 영향받는 라운드를 PLAN에 ‘재검증 필요’로 표시하고 검증담당에게 다시 넘긴다. 검증담당 문서를 대신 통과로 바꾸지 않는다.
- 현재 기준의 독립 검증·연결·영향 기능 회귀검증과 필수 기록 점검을 받은 뒤 SUMMARY·WORK 인계·RESUME를 갱신한다. PLAN을 `검증 중 / 통과`로 두고 `check.py check Rn`을 실행한다. 누락·기준 변경을 해결한 뒤 `완료 / 통과`로 바꾸고 다시 검사한다. 검사 실패를 무시하거나 CHECK를 대신 통과로 바꾸지 않는다. R2는 R1+R2, 마지막은 전체 흐름을 확인한다.
- 범위·핵심 계획 변경은 같은 논점의 개정으로 이유·영향을 기록하고 해당 범위만 재검토/승인받는다. 단순 문구나 꾸미기 변경에 승인 절차를 남발하지 않는다.
- 변경 시 실제 변경 파일·호출/데이터 연결·영향 라운드·다시 확인할 사례를 적는다. 기존 기능을 고치는 일은 기존 실행 범위 안에서 진행한다. 재승인 필요 여부와 재검증 필요 여부를 구분한다. 검증담당이 영향 범위를 검토하고 불확실하면 검증 범위를 넓힌다.

기본은 순차 누적 통합이다. 병렬 구현은 파일 경계·입출력 계약·선행·통합 담당이 분리될 때만 제안한다. 두 세션의 파일 소유권은 공통 규칙을 따른다.

## 이해를 놓치지 않기

핵심 동작·규칙·연결이 추가되거나 달라진 라운드 종료 시 2~3분 정도 확인한다. 단순 꾸미기 변경에는 반복하지 않는다.

1. 3~5줄로 무엇을 만들었는지, 입력→처리→출력, 중요한 선택 이유와 한계를 설명한다.
2. 실제 코드의 핵심 파일·함수와 정상 입력 예 하나를 가리킨다. 여러 구현 세부를 한꺼번에 외우게 하지 않는다.
3. 사람이 출력이나 실패 동작을 먼저 예상하고, 직접 실행 결과와 비교하게 한다. “이해했나요?” 대신 자신의 말로 흐름과 이유를 설명할 기회를 준다.
4. 실제 답변 요약·맞는 부분·보완할 부분·근거를 WORK의 이해 확인에 남긴다. 답변 전에는 ‘내 설명 대기’다. 단순 동의만으로 설명 확인을 만들지 않는다.
5. 이해 확인과 구현 완료·실행 승인을 구별한다. 시간이 부족하면 미확인 항목을 REVIEW에 넘기고 완료했다고 포장하지 않는다.

## 전체 복습과 제출

- REVIEW는 실제 구현·검증 기준으로 갱신한다. 결정 초안이나 폐기한 기능을 현재 동작처럼 쓰지 않는다. 핵심 문장은 코드 위치·결정·검증 근거 중 하나로 연결한다.
- 마지막 30분은 예를 들어 최종 실행10 + 이해 복습10 + 제출10으로 나눌 수 있다. 제출에 더 오래 걸리면 실제 조건에 맞춰 재배정한다. 기능을 더 늘리다가 복습·제출을 없애지 않는다.
- REVIEW의 정상 입력 한 흐름을 처음부터 결과까지 함께 따라간다. 실패 입력도 기대와 실제를 비교한다. 사람의 설명을 듣고 틀린 부분만 근거와 함께 보완한다. 예상 시험문제 목록이나 외울 답안으로 바꾸지 않는다.
- 최종 SUMMARY/제출 문서에는 실행법·핵심 기능·검증 근거·한계·제품 버전·작성자·날짜를 남긴다. 제공 README는 보존하고 필요 시 결과 링크를 덧붙인다.
- 최종 코드에서 제품 전체 테스트 후 `check.py check --all`도 실행한다. 자동 검사 결과를 기능 테스트 결과와 구분해 보고한다.
- 새 세션 전 WORK 마지막 인계와 RESUME 상단에 기준·완료/미완료·열린 질문·유효한 승인·다음 행동을 갱신한다. RESUME 하단에 001부터 짧은 전환 이력을 남긴다. 과거 대화와 결정은 보존한다. 다음 담당자는 현재 파일과 인계가 맞는지 확인하고 범위·다음 행동을 되짚는다.
